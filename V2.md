# brainsim v2 — PRD for the initial build

**Status: draft, unbuilt.** v1 remains the reference implementation.

## Goal

Remove every global operation from the design, so that work scales with *events*
rather than with *units*, and no part of the network waits for the whole.

## Non-goals for the initial build

- **Not** recurrent settling dynamics. Not active inference. Both are about being
  *better*, not bigger, and mixing them in would make it impossible to attribute
  any result to the scaling changes.
- **Not** more units. v2.0 targets the *same* 128-unit scale as v1 and must reach
  parity there first. Scaling is v2.1.
- **Not** new learning rules. Everything that survived ablation in v1 carries over
  unchanged, as a hypothesis to re-test.

## The changes, after probing v1

**Measured, and it changes the plan:**

```
  hidden spikes/tick   6.00 of 80  =  7.5% active
  motor  spikes/tick   5.90 of 8   = 73.8% active
  event-driven saving  5.4x        (NOT the ~1000x this was justified on)
```

The event-driven case rested on tick-rate ÷ firing-rate. At biological rates
(~1-5 Hz against a 1 kHz tick) that is ~1000x. **At OUR rates it is 5.4x**,
because the motor layer fires three ticks in four. Batching + JIT beats that
comfortably, so event-driven is **demoted from a founding change to a
conditional one**.

| global chokepoint in v1 | v2 | status |
|---|---|---|
| k-WTA ranks all units against each other | **local pools** | founding |
| trials halt everything every 30 ticks | **continuous time** | founding |
| one neuromodulator scalar for the whole net | **parallel loops** | founding |
| every unit evaluated every tick | event-driven | **conditional** — only after motor sparsity is fixed |

**New prerequisite: fix motor sparsity — and v1 says this is not free.**
73.8% motor activity is wildly unbiological, and it is the same fact behind v1's
hardest problem: when almost every motor cell fires, `outer(fm, trh)` credits
almost all of them, which is why credit assignment needed `TAGGATE` and why the
class cliff existed at all.

**But v1 already tried a 1-of-N motor layer and it FAILED**
(`19_local_alternatives.py`): 0.319 / 0.158 at 4 and 8 classes -- no better than
baseline -- and 2 classes fell 1.000 -> 0.667. The recorded reason: *per-tick
winners smear credit, because the decision is a 30-tick aggregate.*

The claim survives into v2 **only because continuous time removes that
aggregate.** With no decision boundary the action IS whatever fires, so a per-tick
winner and the decision are the same event -- exactly the misalignment that broke
it in v1. That is a plausible argument, not a result. **Treat as a hypothesis to
test at M0, not a prerequisite to assume.** If it fails again, event-driven stays
conditional forever and the founding changes reduce to three.

**Tension to respect:** event-driven (sparse, irregular, data-dependent) and
batched vectorisation (dense, regular) pull in opposite directions. At 128 units
and 7.5% activity, dense-batched wins. Event-driven only becomes correct at much
larger scale with much lower firing rates -- which is exactly why it is
conditional, and why it must not be assumed while designing the batched core.

## Build it fast from day one

Not a later refactor. The speed work is cheap at the start and expensive to
retrofit, and this project's dominant failure has been measurement -- more seeds
per unit time is a *correctness* investment, not a comfort one.

- **Batched over agents from the first commit.** State is `(A, N)` not `(N,)`.
  Retrofitting a batch axis through replay, working memory and per-agent RNG is
  the kind of change that silently breaks numbers.
- **numba `@njit` on the hot loop**, written to its supported subset from the
  start: plain arrays, no class attributes in the kernel, manual top-k rather
  than `np.partition`.
- **Pre-generate random draws in numpy and pass them in as arrays.** numba has
  its own RNG and batched draws differ from N separate draws, so bit-exactness
  breaks otherwise -- and bit-exactness against v1 is how M0 parity is proven.
  This constraint has to be designed in; it cannot be added later.

- **Fixed connectivity is generated from a seed, never stored.** `W_in` is fixed
  in v1 and stored as an array. Generate indices *and* weights from a seed
  instead, so fixed synapses cost **zero memory** at any scale. This is the
  single largest scaling lever (10x, and the only one graded SOLID below), and
  like batching it is nearly free now and a refactor later -- every experiment,
  checkpoint and replay path would otherwise assume a materialised `W_in`.
  Cerebellum is built this way: mossy->granule fixed, granule->Purkinje plastic.

- **Stay inside the numpy/torch intersection.** Prefer operations that exist in
  both (`topk` over `partition`, explicit masks over fancy indexing, no
  numpy-only idioms in the hot path). Costs nothing now; it is the difference
  between a mechanical port to GPU later and a rewrite.

## Does this open a GPU path?

**Short answer: yes, and mainly because of batching from day one.** The detail
below, starting with the constraint everyone assumes is fixed and is not.

### Ticks are OUR artifact, and axonal delay is the way out

The brain has no global clock. Neurons integrate continuously and fire at
threshold; there is no moment when "all units update". The tick is a
discretisation we chose.

**What decouples real neurons is axonal delay.** If the minimum delay between any
two connected neurons is `d`, every neuron can advance independently for `d`
without hearing from anyone -- nothing emitted in that window can arrive yet.
That is how NEST and SpiNNaker parallelise: **the minimum synaptic delay IS the
lookahead window.**

**Our sequentiality is self-inflicted.** The Part 1 design specified
`.delay in 1..20 ticks`; the implementation dropped it and uses a uniform 1-tick
delay, so the lookahead is exactly one tick. (Third thing the design specified
and the code abandoned, after the homeostatic `BODY`.)

Restore it with a **floor**, not just a range: lookahead is the MINIMUM delay, so
delays of 1..20 still give a lookahead of 1 if any synapse has delay 1. A 0.2 ms
tick with a >=1 ms minimum delay -- both biologically right -- gives 5-10 steps of
free parallel advance between synchronisations.

Rare win-win: **more faithful AND more parallel**, from something already in the
original design.

### What makes v2 GPU-capable where v1 is not

Three of the founding changes are
GPU-positive: batched state is the enabler; local pools turn one global top-k
into a batched `topk` along an axis (more GPU-friendly than a global sort); and
removing trial boundaries removes a barrier that would force a kernel sync every
30 ticks. The one GPU-hostile idea, event-driven gather/scatter, was already
demoted on its own merits -- a lucky alignment.

**One real problem remains, plus one that dissolves at the scale where GPU is
worth using:**

1. **Per-tick launch overhead — dissolves with scale.** This and "GPU is not
   worth it at small scale" are the SAME fact: wherever a GPU earns its place,
   the overhead has already amortised.

   ```
     128 units, delay floor 5   ~32,000 FLOP per launch vs ~5 us overhead   ruinous
     10^5 units                 ~5e8 FLOP/tick ~ 50 us vs 5 us              ~10%
     10^6 units                                                             ~1%
   ```

   The 128-unit regime is exactly where the PRD already prescribes CPU+numba.
   Three overlapping mitigations exist if it ever binds: an axonal delay floor of
   k cuts launches k-fold (see above), scale makes work per launch dwarf the
   overhead, and a fused kernel remains available -- made *simpler* by the delay
   floor, since no synchronisation is needed inside the window.
2. **Replay's storage — designed below.** Central to v1's best result
   (lock 9.5 -> 419), so expensive to get wrong.

   **Raggedness is the stated problem; MEMORY is the binding one:**

   ```
                     dense/agent    sparse/agent
     v1 (128 units)      2.6 MB        0.19 MB     13x
     10^4 units        320.0 MB        3.20 MB    100x
     at 1000 agents:   320 GB    vs    3.2 GB
   ```

   **Design = 1 + 2 + 3 together** (3 is free given 1):

   1. **Fixed-length windows into a flat ring buffer.** Stop storing episodes.
      Keep a per-agent circular buffer of `(state, action, reward)`; an episode
      is a fixed-length window ending at a chosen timestep. Raggedness vanishes
      by construction -- every window is length L, uniform tensor, no padding.
      **Also answers Q4** (what delimits an episode without a done flag), and v1
      already does this de facto: `HIPPO_WINDOW=20` exists precisely because
      `lock-10` only signals done at the goal. One change, three problems.
   2. **Sparse index storage.** The hidden code is k-sparse by construction, so
      storing n floats for k active units wastes 13x now and 100x at scale.
      Store `(uint16 index, float16 value)` and scatter to dense on use. This is
      what lets replay survive above ~10^4 units at all.
   3. **Batched reverse pass.** Falls out of 1: L sequential batched steps,
      parallel across agents and across sampled windows. The dependency WITHIN a
      window is irreducible -- reverse TD needs each successor's fresh value,
      which is the entire 80x effect -- but L is small.

   **Deferred, as separate research rather than infrastructure:**

   4. **Regenerate rather than store.** Keep only the stimulus; re-run the
      forward pass at replay. Memory becomes negligible, but the network has
      changed since encoding, so regenerated states differ from the originals.
      That is *reconstructive* memory, not replay -- arguably more biological,
      definitely a different mechanism, needs its own validation.
   5. **Generative replay.** Step 11's learned forward model: replays what did
      NOT happen, which is planning. Highest ceiling, highest risk (model errors
      compound). Needs a working forward model first.

### Single instance vs many agents

Both paths open, at different scales -- and local pools make them the same code.

A single instance has parallelism WITHIN a tick, and -- once axonal delays have a
floor -- across the next k ticks too (see above). At v1's uniform 1-tick delay
the cross-tick factor is 1, so the figures below assume the worst case. The
parallel work per tick is the size of the network:

```
   128 units        ~3,200 MACs/tick    << GPU launch overhead. Useless.
   10^5 units       ~10^8 ops/tick      fills a GPU properly.
   10^6 units       ~10^9 synapses      ~12 GB of state at 12 B/synapse; fits one GPU.
   10^8 units       does not fit        needs partitioning across devices -- see below
```

**Multi-GPU partitioning is tractable, and our founding changes are what make it
so.** An earlier draft said "nobody has designed this", which was wrong on two
counts: it has been designed (NEST distributes across thousands of cores;
SpiNNaker was purpose-built for it), and local pools plus a delay floor are
precisely the two properties that make it work.

"Unit" means neuron throughout. **But memory scales with SYNAPSES, and the
multiplier is fan-out -- a parameter we have never chosen deliberately.**

```
  v1 actual fan-out:  10 incoming + 16 outgoing = ~26 synapses per hidden unit
  biology:            ~1,160 brain-wide average, ~7,000 cortical

  memory at 1e8 NEURONS, by fan-out:
    fan-out   26:  2.6e9 synapses      31 GB  ->    1 GPU
    fan-out  100:  1.0e10 synapses    120 GB  ->    2 GPUs
    fan-out 1000:  1.0e11 synapses  1,200 GB  ->   15 GPUs
    fan-out 7000:  7.0e11 synapses  8,400 GB  ->  105 GPUs
```

**The GPU count at any scale is set by a fan-out spanning two orders of
magnitude**, between what we have and cortical density. At v1's actual
connectivity 10^8 neurons would fit one GPU -- but that is not good news, it is
an unexamined parameter. Ours is ~26 because `W_in` is 25%-dense over a 40-input
layer, which is fine at 80 units and almost certainly not viable at 10^8:
connectivity is what lets information mix, and 10 inputs per neuron across a
hundred million units gives a hundred million nearly-independent tiny circuits
rather than a brain.

Scaled at a biological fan-out of ~1,000:

```
   1e7 units    1.0e10 synapses     0.1 TB  ->      2 GPUs
   1e8 units    1.0e11 synapses     1.2 TB  ->     15 GPUs
   1e9 units    1.0e12 synapses    12.0 TB  ->    150 GPUs
   86e9 (brain) 1.0e14 synapses  1197.1 TB  -> ~15,000 GPUs
```

### Can brain scale be reached without thousands of GPUs?

Four architectural levers, multiplicative:

```
  naive (12 B/synapse, fan-out 1000)   1032.00 TB  -> 12,900 GPUs
  + rank-1 eligibility                  344.00 TB  ->  4,300
  + int8 weights                         86.00 TB  ->  1,075
  + 90% fixed connectivity (seed-gen)     8.60 TB  ->    108
  + granule-style fan-out for the bulk    0.17 TB  ->      2
```

**Solid.** *Fixed random connectivity is free* -- regenerate indices AND weights
from a seed; only PLASTIC synapses cost memory. `W_in` is already fixed, and
cerebellum is built this way (mossy->granule fixed, granule->Purkinje plastic).

**Plausible, untested.** *int8 weights.* Real synapses are thought to store ~4-5
bits, so this is more precision than biology -- but quantisation interacts with
small local updates and must be validated.

**Overstated.** *Rank-1 eligibility.* Ours is `elig*d + (1-d)*outer(fm, trh)`, a
decaying SUM of outer products, which is not rank-1. Keeping pre/post traces and
forming the product on demand is the standard three-factor approximation, but it
is a DIFFERENT RULE. This project has learned repeatedly that "should be
equivalent" is not. Do not count it until measured.

**Changes the target.** *Granule fan-out.* 69e9 granule cells have ~4 inputs
each, but their parallel-fibre OUTPUTS contact many Purkinje cells, and the brain
has ~1e14 synapses regardless. So the last row is brain-scale NEURON count with
600x fewer connections -- a very large, very thin network, not a small brain.

**The honest split:**

- **Brain-scale NEURONS: ~2-100 GPUs** with these levers.
- **Brain-scale SYNAPSES (1e14): ~1,000 GPUs minimum**, even at 1 B each with
  eligibility removed. That floor is hard.

Synapses are probably what matters -- they are where memory and learning live.
Any future claim about "brain scale" must say which of the two it means.

### CPU vs GPU at brain scale -- the binding constraint flips

```
                        capacity      bandwidth     binding
  GPU (80 GB, 3 TB/s)   1,075 devs      57 devs     capacity  -> ~134 nodes of 8
  CPU (6 TB, 1 TB/s)       14 nodes    172 nodes    bandwidth -> ~172 nodes
```

**A CPU node holds ~75x more state than a GPU** (~6 TB DRAM vs 80 GB HBM). The
GPU path needs 1,075 devices for MEMORY but only 57 for bandwidth -- nineteen
times more accelerators than the traffic requires, bought purely to rent HBM,
with the tensor cores idle. That is a mismatch signal, not just a cost.

CPUs are also better at the irregular, data-dependent access event-driven
simulation needs: scattered gathers with unpredictable indices suit branch
predictors and large caches, and defeat SIMD lanes.

**This is what the field does.** NEST runs on CPU clusters; SpiNNaker uses ARM
cores; large brain-simulation efforts have run on CPU supercomputers, not GPU
farms.

**The two regimes want opposite hardware:**

- **small scale, many agents, dense batched -> GPU.** M0/M1, and all near-term work.
- **large scale, single instance, sparse event-driven -> CPU.** The brain-scale end.

**This partly rehabilitates event-driven**, demoted earlier because it buys only
5.4x at our firing rates on dense-batched hardware. At brain scale on CPUs,
sparse irregular access is exactly what the machine is good at, and event-driven
is what makes the workload tractable at all. Keep it conditional for M0/M1;
expect it to become founding at the scale-out end.

### A cluster, necessarily -- but a modest one

There is no single-machine option: practical maximum is ~2-8 sockets and a few
TB of DRAM, and 86 TB at 172 TB/s is not a box you can buy.

```
  standard 2-socket, 512 GB   capacity 172 nodes   bandwidth 172 nodes  -> 172
  fat node, 2 TB              capacity  43 nodes   bandwidth 172 nodes  -> 172
```

Interconnect is the easy part: **34 GB/s aggregate** if 10% of spikes cross
nodes, against ~50 GB/s per InfiniBand link -- because spiking sends *indices*,
not activation vectors. Local pools keep most traffic on-node; the delay floor
batches the exchanges.

**Memory capacity is a hard floor that slowing down cannot cross.** Running
slower than real time reduces the BANDWIDTH need but not the need to hold 86 TB.
The cheap configuration is fat nodes plus relaxed timing: at 2 TB/node, capacity
needs 43 and bandwidth at 10x-slower needs 17, so **~43 fat nodes**. This is why
brain-simulation projects habitually run far slower than real time.

**Both numbers depend on two UNTESTED assumptions:** int8 weights, and no
per-synapse eligibility (Q5). At v1's actual 12 B/synapse it is 1.2 PB and ~600
fat nodes. The cheap configuration is contingent on measurements not yet taken.

### Why silicon needs so many devices -- it is NOT feature size

Counterintuitively, chips have *finer* features than synapses: a transistor is
~20-40 nm, a synapse ~1,000 nm across. Silicon wins there by an order of
magnitude. The gap comes from three other things:

1. **Dimensionality.** 1e14 synapses in 1.3 L is ~13 um^3 each, in 3D. An H100
   die is ~814 mm^2 of essentially planar silicon with a few microns of active
   layer. The brain is not finer-grained, it is VOLUMETRIC. This is most of the
   density gap.
2. **Memory IS compute.** A synapse stores its weight and multiplies in the same
   structure. On a GPU weights live in HBM and the ALUs are elsewhere, so every
   operation moves data -- which is why the estimate above needed 800 TB/s of
   *bandwidth* alongside capacity. The bandwidth wall is a von Neumann artifact
   biology does not have.
3. **Precision.** A synapse holds ~4-5 bits of analog molecular state. We use
   float32 -- 6-8x more precision than the thing being imitated, 1e14 times over.

The brain buys this by being ~10^7x slower per element and not caring, because
10^11 of them run at once. The bill in silicon: **700 kW vs 20 W, ~35,000x the
power** for a comparable synapse count.

**Consequence for this roadmap: only precision is fixable in software.** The int8
lever attacks it and could go to 4 bits. Seed-generated connectivity and rank-1
eligibility attack *capacity*, which is a symptom. Dimensionality and
memory-compute separation are hardware properties that no architecture work
touches -- which is the real argument for neuromorphic hardware (Loihi,
SpiNNaker): not that it is more brain-like in spirit, but that co-locating memory
with compute and accepting low precision is exactly what this analysis says is
needed.

**Open: what fan-out does the architecture need?** Untested at every scale. It
dominates every memory estimate here, and local pools interact with it directly
-- pool size bounds how much of a neuron's fan-out stays on-device.

**Memory capacity is the only wall; communication is free.** Inter-device spike
traffic at 10^8 units is ~0.4 GB/s against NVLink's ~900 GB/s, because spiking
networks send **indices, not activation vectors** -- at 1% activity you send 1%
of the data. That is the structural advantage of spiking over dense ANNs for
distribution, and it is why the bottleneck is how much synaptic state fits, not
how fast devices talk.

Two design properties do the work:

- **Local pools** keep nearly all connectivity intra-pool, so assigning pools to
  devices keeps nearly all traffic on-device.
- **The axonal delay floor** sets the exchange interval: with k=5, devices
  synchronise five times less often than per tick.

Not needed below ~10^7 units, which is far beyond M0 and M1. Recorded so the
architecture does not foreclose it.

**Local pools make the two cases computationally identical in shape.** Many
agents is block-diagonal -- N small networks that never interact. One large
network with local pools is ALSO mostly block-structured: pools compete
internally with sparse coupling between them. "1,000 agents x 128 units" and
"1 agent x 128,000 units in 1,000 pools" are nearly the same tensor problem, so
one batched kernel serves both and the codebase does not fork.

**Timeline:** many-agent batching is the near-term win and works at any size.
Single-instance GPU arrives around 10^5 units and lasts to ~10^7. Beyond that
needs a distributed design that does not exist yet.

**Not at M0.** At 128 units a GPU is *slower* than CPU+numba, because launch
overhead dominates tiny work.

## Carried over from v1, unchanged

Three-factor learning with RPE; `V(s)` critic (normalised); reverse replay with TD
bootstrapping; `TAGGATE` credit gating; the WM residual pathway; `ADAPTIVE`
volatility. The task suite with its **measured** floors and ceilings. The method
rules. `HISTORY.md`.

## Interfaces

**Agent.** `emit(t)` returns spikes at time `t`; `sense(spikes, t)` delivers input;
`reward(r, t)` delivers reward *whenever it arrives*. No decision boundary.

**Task adapter.** Existing trial tasks port by presenting a stimulus for a window
and accepting whatever action is emitted during it. A trial task is a continuous
task with a fixed presentation schedule -- so v1 and v2 can be compared on
identical task definitions.

## Milestones

- **M0 — parity.** v2 reaches v1's numbers on **every task in the suite**, same
  measured floors and ceilings. Bit-exact where the pre-generated-RNG design
  allows; within noise across >=6 seeds otherwise. **Nothing else starts until
  this passes.** Also at M0: sweep replay window L, and test the motor-sparsity
  hypothesis that v1 refuted under trials.
- **M1 — throughput.** Demonstrate the batched core scales: agents/second against
  agent count, and units/second against network size, to 10^4 units. Note this
  does NOT test event-driven, which is conditional -- without it, work scales with
  units, not spikes. The earlier wording of this milestone tested a claim the
  probe had already demoted.
- **M2 — local pools earn their place.** Show pooled competition beats global
  k-WTA on the capacity limit v1 measured (0.946 at 4 combos -> 0.385 at 16).
  **Q3 conflicts with M0 here:** pooling may need more total units than v1 has,
  so either M0 parity is measured with pools disabled, or the "same scale"
  non-goal is relaxed for M2. Decide before building, not during.

## Success criteria

v2 replaces v1 only when it **beats v1 on the same tasks against the same measured
floors and ceilings**. Otherwise v1 stays. There is no "it's more principled"
exemption.

## Open questions — probed; Q1 and Q4 resolved, Q2 and Q3 open

**Q1 RESOLVED, and it demoted event-driven.** 7.5% hidden / 73.8% motor activity
gives a 5.4x saving, not ~1000x. See above.

**Q2 OPEN, and it is a real hole.** `elig` is *consumed* at each decision -- that
fix was worth 0.58 -> 0.97 in v1. With no decisions, nothing clears it, and with
tau=200 ticks credit from 200 ticks ago contaminates every update. Continuous
time needs a consumption rule that is not a trial boundary. Candidates: consume
on reward arrival; consume proportionally to how much of the trace was cashed;
or a second faster trace that gates the slow one. **Must be resolved before M0.**

**Q3 OPEN.** v1 already failed at 16 stimulus combinations with 80 units. Four
pools of 20 gives each pool a quarter of a capacity that was already
insufficient, so pooling likely requires MORE total units -- which conflicts with
"same scale as v1" for M0. Resolve by measuring capacity against pool count and
size before committing.

**Q5 OPEN — worth 3x memory at scale.** Is per-synapse eligibility replaceable by
an outer product of pre- and post-traces formed on demand? Ours is
`elig*d + (1-d)*outer(fm, trh)` -- a decaying SUM of outer products, so NOT
rank-1, and the trace-pair version is a genuinely different rule. If it matches
per-synapse eligibility on the suite, per-synapse state drops from 12 B to 4 B
and eligibility stops scaling with synapses at all. If it does not, the levers
table loses its second-largest entry. **Testable in v1 today**, and cheap: swap
the rule, run the suite. Do this before it becomes a scaling assumption.

**Q4 RESOLVED by the replay design above.** Episodes stop being stored objects:
a flat ring buffer plus a fixed-length window ending at a chosen timestep IS the
episode. `done` is no longer needed to delimit anything, and v1 already worked
this way de facto via `HIPPO_WINDOW`.

*Residual risk:* window length L becomes a hyperparameter that replay's whole
value rests on. v1's best result came with `HIPPO_WINDOW=20` and was never swept.
**Sweep L at M0** -- a bad L could cost most of the lock's 9.5 -> 419.
