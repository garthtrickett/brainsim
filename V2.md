# brainsim v2 — PRD for the initial build

**Status: draft, unbuilt.** v1 remains the reference implementation.

## Goal

Remove every global operation from the design, so that work scales with *events*
rather than with *units*, and no part of the network waits for the whole.

## Non-goals for the initial build

- **Not** recurrent settling dynamics. Not active inference. Both are about being
  *better*, not bigger, and mixing them in would make it impossible to attribute
  any result to the scaling changes.
- **Not** more units. v2.0 targets the *same* 128-unit scale as v1 and must reach
  parity there first. Scaling is v2.1.
- **Not** new learning rules. Everything that survived ablation in v1 carries over
  unchanged, as a hypothesis to re-test.

## The changes, after probing v1

**Measured, and it changes the plan:**

```
  hidden spikes/tick   6.00 of 80  =  7.5% active
  motor  spikes/tick   5.90 of 8   = 73.8% active
  event-driven saving  5.4x        (NOT the ~1000x this was justified on)
```

The event-driven case rested on tick-rate ÷ firing-rate. At biological rates
(~1-5 Hz against a 1 kHz tick) that is ~1000x. **At OUR rates it is 5.4x**,
because the motor layer fires three ticks in four. Batching + JIT beats that
comfortably, so event-driven is **demoted from a founding change to a
conditional one**.

| global chokepoint in v1 | v2 | status |
|---|---|---|
| k-WTA ranks all units against each other | **local pools** | founding |
| trials halt everything every 30 ticks | **continuous time** | founding |
| one neuromodulator scalar for the whole net | **parallel loops** | founding |
| every unit evaluated every tick | event-driven | **conditional** — only after motor sparsity is fixed |

**New prerequisite: fix motor sparsity.** 73.8% motor activity is wildly
unbiological, and it is the same fact behind v1's hardest problem: when almost
every motor cell fires, `outer(fm, trh)` credits almost all of them, which is why
credit assignment needed `TAGGATE` and why the class cliff existed at all. A
1-of-8 motor layer would make credit assignment nearly trivial AND make
event-driven pay. One fix, two benefits.

## Build it fast from day one

Not a later refactor. The speed work is cheap at the start and expensive to
retrofit, and this project's dominant failure has been measurement -- more seeds
per unit time is a *correctness* investment, not a comfort one.

- **Batched over agents from the first commit.** State is `(A, N)` not `(N,)`.
  Retrofitting a batch axis through replay, working memory and per-agent RNG is
  the kind of change that silently breaks numbers.
- **numba `@njit` on the hot loop**, written to its supported subset from the
  start: plain arrays, no class attributes in the kernel, manual top-k rather
  than `np.partition`.
- **Pre-generate random draws in numpy and pass them in as arrays.** numba has
  its own RNG and batched draws differ from N separate draws, so bit-exactness
  breaks otherwise -- and bit-exactness against v1 is how M0 parity is proven.
  This constraint has to be designed in; it cannot be added later.

- **Stay inside the numpy/torch intersection.** Prefer operations that exist in
  both (`topk` over `partition`, explicit masks over fancy indexing, no
  numpy-only idioms in the hot path). Costs nothing now; it is the difference
  between a mechanical port to GPU later and a rewrite.

## Does this open a GPU path?

Yes -- mostly because of batching from day one. Three of the founding changes are
GPU-positive: batched state is the enabler; local pools turn one global top-k
into a batched `topk` along an axis (more GPU-friendly than a global sort); and
removing trial boundaries removes a barrier that would force a kernel sync every
30 ticks. The one GPU-hostile idea, event-driven gather/scatter, was already
demoted on its own merits -- a lucky alignment.

**Two problems remain unsolved by this PRD and must be designed if GPU is
pursued:**

1. **Per-tick launch overhead.** Ticks are sequentially dependent, which is
   irreducible. Naively that is one kernel launch (~5 us) per ~6,400 FLOPs of
   work. Needs a persistent or fused kernel running many ticks before returning.
2. **Replay's ragged structures.** Per-agent variable-length episode stores with
   priority sampling. Needs fixed-size circular buffers and padded episodes so
   replay becomes a batched gather. This is central to v1's best result, so
   getting it wrong is expensive.

**Not at M0.** At 128 units a GPU is *slower* than CPU+numba, because launch
overhead dominates tiny work. GPU becomes correct at M1 (10^4 units) or with
thousands of agents.

**Tension to respect:** event-driven (sparse, irregular, data-dependent) and
batched vectorisation (dense, regular) pull in opposite directions. At 128 units
and 7.5% activity, dense-batched wins. Event-driven only becomes correct at much
larger scale with much lower firing rates -- which is exactly why it is
conditional.

## Carried over from v1, unchanged

Three-factor learning with RPE; `V(s)` critic (normalised); reverse replay with TD
bootstrapping; `TAGGATE` credit gating; the WM residual pathway; `ADAPTIVE`
volatility. The task suite with its **measured** floors and ceilings. The method
rules. `HISTORY.md`.

## Interfaces

**Agent.** `emit(t)` returns spikes at time `t`; `sense(spikes, t)` delivers input;
`reward(r, t)` delivers reward *whenever it arrives*. No decision boundary.

**Task adapter.** Existing trial tasks port by presenting a stimulus for a window
and accepting whatever action is emitted during it. A trial task is a continuous
task with a fixed presentation schedule -- so v1 and v2 can be compared on
identical task definitions.

## Milestones

- **M0 — parity.** v2 reaches v1's numbers on all seven tasks, same floors and
  ceilings, same seeds where possible. **Nothing else starts until this passes.**
- **M1 — the scaling claim.** Demonstrate work-per-second scales with spikes, not
  units, by growing to 10^4 units and measuring.
- **M2 — local pools earn their place.** Show pooled competition beats global
  k-WTA on the capacity limit v1 measured (0.946 at 4 combos -> 0.385 at 16).

## Success criteria

v2 replaces v1 only when it **beats v1 on the same tasks against the same measured
floors and ceilings**. Otherwise v1 stays. There is no "it's more principled"
exemption.

## Open questions — probed, with three still open

**Q1 RESOLVED, and it demoted event-driven.** 7.5% hidden / 73.8% motor activity
gives a 5.4x saving, not ~1000x. See above.

**Q2 OPEN, and it is a real hole.** `elig` is *consumed* at each decision -- that
fix was worth 0.58 -> 0.97 in v1. With no decisions, nothing clears it, and with
tau=200 ticks credit from 200 ticks ago contaminates every update. Continuous
time needs a consumption rule that is not a trial boundary. Candidates: consume
on reward arrival; consume proportionally to how much of the trace was cashed;
or a second faster trace that gates the slow one. **Must be resolved before M0.**

**Q3 OPEN.** v1 already failed at 16 stimulus combinations with 80 units. Four
pools of 20 gives each pool a quarter of a capacity that was already
insufficient, so pooling likely requires MORE total units -- which conflicts with
"same scale as v1" for M0. Resolve by measuring capacity against pool count and
size before committing.

**Q4 OPEN.** Episodes are delimited by `done`, a trial concept. In continuous
time `HIPPO_WINDOW` becomes the *only* episode definition. Replay is the
strongest mechanism in v1 (lock 9.5 -> 419); a worse episode definition could
cost most of that.
